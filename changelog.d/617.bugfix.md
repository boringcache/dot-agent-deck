## Six daemon-side pane writes can no longer land in a pane that has changed hands

A pane id is a recycled handle: when an agent exits or is closed, its `DOT_AGENT_DECK_PANE_ID` is free for the next spawn to inherit. Six daemon-side paths could write into a pane keyed by that string alone — five of them always, and the sixth whenever the identity it was passing happened to be absent. Each had a real gap between deciding where the text should go and actually writing it, so if the intended agent went away inside that gap, the text was typed into whatever process had taken its place, and (for everything but the notices) Enter was pressed on it. A tool-capable agent could then act on work it was never given.

Issue #608 closed this at the daemon's write-and-submit handler. This closes the rest of that write family, and closes it by **type** rather than by review: the guarded write APIs (`write_and_submit_guarded`, `write_and_submit_guarded_detailed`, `write_notice_guarded`) now take the expected agent identity as a `&str` instead of an `Option<&str>`. Passing no identity used to skip the identity comparison entirely and fall through to an unguarded write; that case no longer exists to be skipped, and every caller that had nothing to pass became a compile error. Two independent reviews of the #608 fix had each found sites the other missed, which is the argument for letting the compiler enumerate them.

This is a statement about the enumerated *write* paths, not about the pane keyspace in general. The native `get-seed` pull — where an editor extension asks the daemon for a pi pane's stashed seed by pane id — still resolves that id with no identity check, and is tracked separately as **issue #916**.

The six paths, and the window each had:

- **Scheduled tab reuse.** A reuse fire waited out the deliver-on-idle debounce (5s by default, up to 60s under continuous typing) holding nothing but the pane id. The reuse decision also asked only whether *some* live process owned that pane, never whether it was one the task had spawned — although the reuse record has always stored those ids. It now resolves the pane's live agent, checks it against the record, and delivers bound to it. A tab whose agent was restarted in place is no longer recognised as reusable, so the next fire opens a fresh tab instead of re-delivering into it: an extra tab, rather than a scheduled prompt submitted into a process that never ran the task.
- **Dispatch results.** The daemon resolves the caller's directory, then does a git worktree creation and an agent spawn — unbounded, and deliberately outside any state lock — before writing the result back. It now captures the caller's agent id from the same registry record as the directory, and delivers to that.
- **The native-seed PTY fallback.** A pi pane's seed is stashed for the editor extension to pull; if no pull arrives within 15 seconds the daemon types the seed in as a safety net. That timer held only a pane id.
- **Work-done feedback.** A worker's completion report is submitted into its orchestrator's pane, bound to the orchestrator the delegation was *commissioned* by. If the pane that commissioned the delegation is not the pane the completion routes to, the report is now dropped rather than delivered to the pane that happens to be there — it would otherwise arrive labelled as work that orchestrator asked for. Two cases are deliberately weaker and are not claims about who asked for anything: a completion nobody commissioned is bound instead to the pane's current agent, resolved immediately before the write; and because a completion carries no delegation generation, a completion credited to a *superseded* delegation is bound to the orchestrator of the newest delegation on that worker pane rather than to the one that issued the superseded task.
- **Two delegate notices** into the orchestrator pane — the one reporting that a `clear = true` replacement worker is not there, and the one reporting that its respawn failed outright. The first was already guarded but passed through an identity that could be absent, which put it back on the unguarded path in exactly the case where the orchestrator pane had just been freed. The second was unguarded on the reasoning that it reports a failure it learns about immediately; that is an argument about a window's size, not about the write being safe, and the two sibling arms of one `match` no longer disagree about it.

A refused write is **not** retried against whoever now holds the pane — that is the delivery this exists to prevent. A *partial* write is treated separately from a refusal at every one of these sites: bytes of ours already reached the authorised target, so re-sending would duplicate a half-written message rather than repair it.

Binding to an identity means a delivery can now be *refused* where it previously landed somewhere, and both refusals cost something visible. Reuse costs an extra tab, as above. Work-done costs a **lost report**: an orchestrator agent replaced in place — a crash and a respawn on the same pane — keeps its pane but gets a new agent id, so every delegation still outstanding was commissioned against the old one, and each worker's completion is written to the daemon log with nothing surfaced in the pane. That is invisible unless you read `deck.log`.

None of this crosses the TUI↔daemon socket. No message, field or type in the protocol module changed, and no value that used to be accepted over it is now refused, so `PROTOCOL_VERSION` is unchanged at 8 and an older and a newer build interoperate exactly as before.

One interaction is worth naming because it is not obvious. Moving the reuse delivery onto the guarded primitive also subjected it, for the first time, to issue #424's repeat-payload guard — which refuses bytes identical to ones an earlier automatic write left in the pane's input box, once the user has typed since. A scheduled task's prompt is fixed by configuration and therefore identical on every fire, so the previous fire's record would have refused the next one. The reuse path now supersedes the previous fire's confirmation watch and, when that watch was carrying these exact bytes, releases the record it held — finishing an abort that would otherwise complete whenever the runtime got round to it. It releases its own record after a write that reached the target. It does **not** clear a record it did not create: if a fire's write was only partial, the bytes it left in the input box keep guarding, and the next fire is refused rather than submitting the whole prompt on top of them and whatever the user has typed since.
